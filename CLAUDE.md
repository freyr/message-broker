# Freyr Message Broker

Standalone PHP messaging library (PHP 8.4 and 8.5, composer constraint ≥ 8.4): transactional outbox (partitioned PostgreSQL table, no ordering guarantee), consumer-side deduplication and DLQ, an AMQP producer/consumer. No framework coupling, plain PDO on PostgreSQL.

**Core concept.** The aim is a *true* outbox/inbox **exactly-once** layer for the PHP community — at-least-once delivery + consumer-side dedup/DLQ yielding exactly-once *processing*, the semantics that normally demand bespoke per-project glue. This library ships the **AMQP transport only** (RabbitMQ) so teams adopt it within their own infrastructure rather than being forced onto one broker: non-FIFO competing-consumer queues, routed by message name. There is no ordering at all: one `Relay` class (core, behind the `OutboxPublisher` port; the AMQP transport is `AmqpMessagePublisher`), and any number of identical workers drain one lane via `FOR UPDATE SKIP LOCKED` claims, so rows publish in any order and consumers must be order-insensitive. Consumer-side dedup absorbs the duplicates a worker crash can produce. By default the relay marks rows published (`published_at`) and never deletes (`PublishedRows::Mark`); `new PostgreSqlOutboxStore($pdo, PublishedRows::Delete)` deletes each published row in the claim transaction instead (see `storage/postgresql/docs/STORAGE.md`); `message-broker:outbox:maintain` drops expired daily partitions with `DETACH PARTITION ... CONCURRENTLY` (PostgreSQL 14+, so there is no DEFAULT partition and partitions are created ahead; pg_partman may create them). An expired partition that still holds unpublished rows is kept by default (reported, and the command exits with FAILURE); `--drop-unpublished` drops it with those rows (the retention period then is a hard age limit). Scope is **PostgreSQL + AMQP only**: there is no ordering of any kind (no per-lane order, no per-key FIFO, no Kafka transport). Research + decisions live in the vault.

Messages are JSON (`JsonWireFormat`, `JsonDeserializer`). Encoding happens at **produce time** (the outbox `body` BYTEA column holds the final wire bytes, payload only; produce-time headers live in a `headers` JSONB column); the PHP relay is a pure byte-pump that builds the `x-message-id`, `x-message-name` and `x-created-at` transport headers from the `id`, `message_name` and `created_at` columns. A payload that cannot be encoded fails at produce. There is no Avro and no schema registry.

Design spec and research notes live in the vault: `~/Vaults/Freyr/message-broker/`.

## Layout

Five Composer packages, each with its own version and tag, in one repo. The core is at the repo root; each adapter is one folder `<role>/<technology>/` that holds all its files (`composer.json`, `src/`, `tests/`, `docs/`, `phpunit.xml.dist`, `infection.json5`, `README.md`, `CHANGELOG.md`, `LICENSE`, `.gitattributes`) and depends on no other folder of the repo. The release workflow copies each adapter folder to a read-only repo with the name of the package (see "Release"). Development, issues and pull requests stay in this repo.

- The core, `freyr/message-broker`: `src/`, `tests/`, `docs/`, namespace `Freyr\MessageBroker\`. Ports, relay loop, delivery processor, console commands, wire format, retry, and the webhook delivery queue in `src/Webhook/` (ports `SubscriptionProvider`, `DeliveryStore`, `DeliverySender`, `DeliveryRetryPolicy`, `DeliveryRetention`, and the flow control ports `RateLimiter`, `CircuitBreaker`, `LaneStates` with the values `Rate`, `RateLimits`, `CircuitBreakerPolicy` and the shared rules `PermitDivision`; `WebhookProducer`, `DeliveryLoop`; see `docs/WEBHOOKS.md`). No `PDO`, no `PhpAmqpLib`, no adapter class in its code, and no `{@see}` to an adapter class in its docblocks.
- `storage/postgresql/`, `freyr/message-broker-storage-postgresql`, flat namespace `Freyr\MessageBroker\Storage\PostgreSql\` (stores, retention, schema installer, `PdoTransaction`, rate limiter and circuit breaker of the webhook lanes). Provides `freyr/message-broker-storage-implementation`.
- `transport/amqp/`, `freyr/message-broker-transport-amqp`, flat namespace `Freyr\MessageBroker\Transport\Amqp\` (consumer, publisher, wait queue, configs). Provides `freyr/message-broker-transport-implementation`.
- `webhook/http/`, `freyr/message-broker-webhook-http`, flat namespace `Freyr\MessageBroker\Webhook\Http\` (`HttpDeliverySender` implements `Webhook\DeliverySender` with Symfony HttpClient; `StandardWebhooksSigner`, `ResponseClassifier`, `HttpSenderConfig`). Provides `freyr/message-broker-webhook-sender-implementation`.
- `ratelimit/redis/`, `freyr/message-broker-ratelimit-redis`, flat namespace `Freyr\MessageBroker\RateLimit\Redis\` (`RedisRateLimiter` implements `Webhook\RateLimiter` with two Lua scripts in `Lua/`, run through the port `RedisScriptRunner` with the bridges `PhpRedisScriptRunner` (`\Redis`, `\RedisCluster`, Relay) and `PredisScriptRunner`; `RedisRateLimitConfig` holds the key prefix of the hash tag `{mb-rl:<prefix>}`). It requires no Redis client: `ext-redis` and `predis/predis` are in `suggest` and `require-dev`. Redis 7.0+ or Valkey 7.2+. Provides `freyr/message-broker-ratelimit-implementation`.

The package name is `freyr/message-broker-<role>-<technology>` and the namespace `Freyr\MessageBroker\<Role>\<Technology>\`; the class names keep their technology prefix. A new adapter follows it (`transport/sqs/`, `freyr/message-broker-transport-sqs`). The adapter namespaces nest in the core namespace: no core folder may have the name of an adapter namespace (`src/Webhook/Http/`, `src/Storage/PostgreSql/`). Each adapter requires one minor line of the core (`^0.15`); `transport-amqp` and `webhook-http` have `storage-postgresql` in `require-dev` for their tests.

The root `composer.json` is the manifest of the core (no `replace`). Its development part installs the four adapters from their folders: path repositories (symlinks in `vendor/`), the adapters in `require-dev` with `*@dev`, and the test namespaces of the adapters in `autoload-dev`. The adapters require the core `^0.15` and the root package is the core, so Composer needs `COMPOSER_ROOT_VERSION` (set in `compose.yaml` and in `tests.yml`).

An adapter imports the core and its own package only, never another adapter. Deptrac enforces these rules (`deptrac.yaml`, each layer selected by the folder of its package): the core uses no adapter, no `PDO` and no `PhpAmqpLib`; the PostgreSQL adapter uses no `PhpAmqpLib`; the AMQP adapter uses no `PDO`; only the HTTP adapter uses `Symfony\Component\HttpClient`, `Symfony\Contracts\HttpClient` and `Symfony\Component\HttpFoundation`; only the Redis adapter uses `Redis`, `RedisCluster`, `Relay\` and `Predis\`. Tests follow the same split: `tests/` (the core: no database, no broker), `storage/postgresql/tests/` (needs PostgreSQL), `transport/amqp/tests/` (needs RabbitMQ and PostgreSQL), `webhook/http/tests/` (unit tests with `MockHttpClient`; functional tests against the webhook test server `tools/webhook-test-server/server.mjs`, and an end-to-end test that also needs PostgreSQL) and `ratelimit/redis/tests/` (needs Redis only; the contract test runs one time with each bridge), run as the PHPUnit suites `core`, `storage-postgresql`, `transport-amqp`, `webhook-http` and `ratelimit-redis` of the root `phpunit.xml.dist` (the whole repo). Each package also has a configuration of its tests alone: `tests/phpunit.xml.dist` for the core, `phpunit.xml.dist` of each adapter folder. A test of an adapter never imports the test namespace of the core (`Freyr\MessageBroker\Tests\`) or of another adapter; what adapter tests share comes from the test kit (below). The upgrade guide (`UPGRADE.md`) has the table of the old and new package names and namespaces. The documents follow the same split: `docs/` (relay, delivery processor, ports, CLI, DLQ, production, test kit, and `QUICKSTART.md`, which uses the core and the four adapters) and the `docs/` folder of each adapter (`storage/postgresql/docs/`: tables, retention, pooling, webhook storage; `transport/amqp/docs/`: transport, consumer, dead letters; `webhook/http/docs/`: HTTP sender, signature, network rules; `ratelimit/redis/docs/`: the Redis rate limit store). A document links to a document of another package and never repeats it; a link from an adapter folder to a file outside it is an absolute link to `https://github.com/freyr/message-broker/blob/main/...`, because the split repo holds only the folder. Each package has its `README.md` (the core: the root `README.md`), and each adapter its `CHANGELOG.md`; the README of an adapter says that issues and pull requests go to this repo.

### Test kit

`src/Testing/` (namespace `Freyr\MessageBroker\Testing\`) is in `src`, not in `tests`, because an adapter installs the core package, whose download has no `tests`. It holds, and may use PHPUnit (so `phpunit/phpunit` is in `suggest`):

- The abstract contract test cases `OutboxStoreContractTestCase`, `DeduplicationStoreContractTestCase`, `DeadLetterStoreContractTestCase`, `TransactionContractTestCase`, `OutboxPublisherContractTestCase`, `DeliveryStoreContractTestCase`, and for the webhook flow control `RateLimiterContractTestCase` (with the hook `ageBuckets()`: no test sleeps for the refill), `CircuitBreakerContractTestCase` and `LaneStatesContractTestCase` (no time hook: the cases of the return, the block and the recovery wait with a bounded poll of at most 2 s). An adapter test extends one, returns its implementation from the abstract factory method, and inherits the tests. The tests state the contract of the port and never a detail of PostgreSQL or RabbitMQ. A new adapter (MySQL, SQS) must extend them.
- The in-memory fakes `InMemoryOutboxStore`, `InMemoryDeduplicationStore`, `InMemoryDeadLetterStore`, `InMemoryTransaction` (the in-memory stores join it and roll back with it), `FakeOutboxPublisher`, `RecordingDeliveryControl`, and for the webhook queue `InMemoryDeliveryStore` (dead letters go to an `InMemoryDeadLetterStore`), `FakeDeliverySender`, `InMemorySubscriptionProvider`, `InMemoryRateLimiter` and `InMemoryCircuitBreaker` (also a `LaneStates`). Each fake passes the same contract test case as the real implementation (`tests/Testing/`).
- Small helpers: `OrderPlaced`, `Unserializable`, `Recording*`, `StubDeduplicationStore` and the trait `TestIsolation` (`isolated()` names for parallel workers).

`storage/postgresql/src/Testing/PostgreSqlTestSupport` (namespace `Freyr\MessageBroker\Storage\PostgreSql\Testing\`) is the PostgreSQL part (connection, schema, `TEST_TOKEN` database); the tests of `transport-amqp` and `webhook-http` use it too. `ratelimit/redis/src/Testing/RedisTestSupport` is the Redis part (the clients from `REDIS_HOST`, a key prefix with `TEST_TOKEN`). Test code in `Testing/` is not mutated (Infection) and not counted as coverage. See `docs/TESTING.md`.

## Deployment

Kubernetes only. Each worker (relay, consumer, webhook delivery loop) is the only process of its container and runs in a `Deployment`; Kubernetes starts the container again after each exit, exit code 0 included, and HPA or KEDA changes the number of pods. The commands that end after one run (`outbox:maintain`, `webhook:maintain`, `dedup:cleanup`, `dlq:import`) run in a `CronJob`. The library has no fork, no worker pool and no process supervisor, and the documents give no instructions for systemd or Supervisor. See `docs/PRODUCTION.md`.

## Connection pooling

No component holds a session-scoped lock. The relay and the consumer use only transaction-scoped locks. Transaction mode works behind pgbouncer when the pooler supports protocol-level prepared statements: `max_prepared_statements` above 0. Tested in CI (job `pgbouncer`, and `make test-pgbouncer`) with pgbouncer 1.26.1, the value 200 and forced rotation of server connections; the guard test `PoolerRotationGuardTest` proves the rotation. The setting exists since pgbouncer 1.21.0 (pgbouncer documentation); versions before 1.26.1 are not tested. pdo_pgsql sends the prepare and the execute as separate round trips, so with `max_prepared_statements = 0` the library fails with `prepared statement "pdo_stmt_…" does not exist`, also outside a transaction: not supported. With the value 0 and `PDO::ATTR_EMULATE_PREPARES => true`, one run of the same suites gave the same result as the supported setting, with the same one test that does not work behind a pooler; CI does not run this variant. `outbox:maintain` and `setup:schema` were tested on a direct connection only. See `storage/postgresql/docs/CONNECTION_POOLING.md`.

## After every code change

Run quality gates and tests through Docker (never host PHP):

```
docker compose run --rm php vendor/bin/phpunit
docker compose run --rm php vendor/bin/phpstan analyse --memory-limit=-1
docker compose run --rm php vendor/bin/ecs check
docker compose run --rm php vendor/bin/deptrac analyse
```

Functional tests need PostgreSQL, RabbitMQ, the webhook test server and Redis — all four in compose. The test server is `tools/webhook-test-server/server.mjs` (Node.js, built-in modules only): the compose service `webhook-server` (started by `depends_on` of `php`), and the `webhook-http` tests find it through `WEBHOOK_SERVER_URL` (default `http://webhook-server:8080`). The CI workflow starts no compose: each job that runs the suite `webhook-http` (functional tests, mutation tests, the package jobs, the lowest jobs, PHP 8.6 advisory) starts the server as a background process and sets `WEBHOOK_SERVER_URL=http://localhost:8080`; a new such job needs the same step. Each test uses its own path prefix of the server's request log (`GET /_requests?prefix=`), so parallel workers can share one server.

The suite `ratelimit-redis` needs the compose service `redis` (`redis:7-alpine`, started by `depends_on` of `php`; the tests find it through `REDIS_HOST`, default port 6379). In CI, each job that runs the suite `ratelimit-redis` (functional tests, mutation tests, the package jobs, the lowest jobs, PHP 8.6 advisory) has a `redis` service container, `REDIS_HOST=127.0.0.1` and the `redis` extension in `setup-php`; a new such job needs the same. The job `valkey` (in the needs of `ci-gate`) runs the suite `ratelimit-redis` against `valkey/valkey:8-alpine`.

The image builds on PHP 8.4 by default. To run on another version, rebuild with the build argument: `PHP_VERSION=8.5 docker compose build php`. CI tests 8.4 and 8.5 and runs PHP 8.6 as an advisory job.

## Mutation testing

Infection measures the quality of the tests; pcov (in the Docker image) collects the coverage of the whole repo without `vendor/` (the path packages in `vendor/` are symlinks, and PHP reports the real path of each file). Infection runs only in CI, not locally. Each package has its own configuration, with its code and its own tests only: the root `infection.json5` is the core (its PHPUnit configuration is `tests/phpunit.xml.dist`, through `phpUnit.configDir`), and the `infection.json5` of each adapter folder is that adapter. The development configuration `infection.repo.json5` is the gate of the whole code: the `src/` folders of all five packages with all suites (`make infection`, about 1 minute; reports go to `var/infection/`, and `infection.html` lists each escaped mutant).

The thresholds (`minMsi`, `minCoveredMsi`) come from measured values: whole code 96 (measured 97.86% on `main` at 0.14.2), core 95, storage-postgresql 95, transport-amqp 97, webhook-http 94, ratelimit-redis 97 (measured alone on `main` at 0.14.2: core 96.92, postgresql 96.58, http about 95, amqp and redis 100; the amqp and redis packages have few mutants, so their thresholds keep a margin). Raise them when the tests improve; never lower them.

CI runs `infection.repo.json5` on the changed lines of `src/` and of the `src/` folder of each adapter on each pull request (job `mutation`, part of `ci-gate`), and the full run on `main`. On `main` the package job of each package (PHP 8.4) also runs Infection with the configuration of the package. A pull request whose changed lines score below the threshold fails: add or tighten the tests that the escaped mutants show.

Parallel workers are isolated. Infection sets `TEST_TOKEN` for each worker; the functional base classes (`FunctionalTestCase`, `AmqpFunctionalTestCase`, both use `Storage\PostgreSql\Testing\PostgreSqlTestSupport`) then use the database `<name>_t<token>` (created on first use) and appends `_t<token>` to queue and exchange names. Pass every AMQP queue or exchange name of a functional test through `self::isolated()`.

## Packages and split rehearsal

`make split-rehearsal PACKAGE=<core|storage-postgresql|transport-amqp|webhook-http|ratelimit-redis> [ARGS=--infection|--lowest]` (script `tools/split-rehearsal.sh`, runs in the `php` service) copies the chosen package and the packages that it needs to a temporary folder, installs the chosen one alone through Composer path repositories (no package of this repo comes from Packagist) and runs its tests alone with its own PHPUnit configuration. The core is copied from the root files with the development part of the root `composer.json` removed; an adapter is its folder as it is. Each path package gets the lowest version that the constraint of the package under test accepts (`^0.15` gives 0.15.0). It fails when a package needs a class of another package that its manifest does not give. `--lowest` (adapters only) takes the core from Packagist at the lowest version of the constraint and keeps every other dependency at its newest version.

CI runs it as the package job (`split-rehearsal` in `tests.yml`, part of `ci-gate`): one entry for each package and PHP version (8.4 and 8.5), with all services and the webhook test server, and with `--infection` on `main` (PHP 8.4). The advisory job `lowest` (each adapter with `--lowest`) runs on each pull request and in `release.yml` after the `packagist` job; it has `continue-on-error` and is not in the needs of `ci-gate`, because a pull request can use a core method that Packagist does not have yet. A failure on `main` means that the adapter needs a higher core floor (`^0.15.4`): a patch release of the adapter raises it.

At each minor release of the core, change together: the core constraint in the `composer.json` of each adapter folder (and the requirement in its `README.md`), `COMPOSER_ROOT_VERSION` in `compose.yaml` and in `.github/workflows/tests.yml`, and then release each adapter with the new constraint.

## Release

The PR title is the only release input (freyr/.github release action, `.github/release.json`). Each package with changed files gets the bump level of the title; on 0.x a breaking title gives a minor release. The core is the package at the path `.` with the tag `v{version}`; its `ignore` list holds the adapter folders, the tools, the tests, the documents and the development configuration. Each adapter has the tag `<role>-<technology>-v{version}` (for example `storage-postgresql-v0.1.0`), the initial version 0.1.0, and an `ignore` list of its own `tests/**`, `docs/**` and `*.md`. Composer and Packagist skip the adapter tags as versions of the core. Check a title with `python3 -I <freyr/.github>/scripts/freyr_release.py plan --base origin/main --title "<title>"`.

`release.yml` on each push to `main`: the job `release` creates the tags; the job `split` (after it) pushes each adapter folder to `main` of its read-only repo `freyr/message-broker-<role>-<technology>` with `danharrin/monorepo-split-github-action` and a token of the release App limited to the four split repos, and pushes the tag `v{version}` of each released adapter there (Packagist reads that repo); the job `packagist` (after it) is a matrix with one entry for each released package (`fail-fast: false`; the core: this repo, an adapter: its split repo) and runs only when a package is released or on a manual run (the manual run releases a core version only). One job does all split pushes in order, so no two pushes to a split repo race. A failed split push or Packagist call fails the run; a new run of the failed jobs repeats it. The split repos accept no direct work: only the release App may push to their `main` and create their `v*` tags.

The core download from Packagist leaves out the adapter folders and the tools through `export-ignore` in the root `.gitattributes`; each adapter folder has its own `.gitattributes` for its split repo.
