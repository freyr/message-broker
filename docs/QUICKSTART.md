# Quickstart

This walkthrough wires up one lane end to end: define a message, produce it
inside your own database transaction, run the schema setup, relay it over
AMQP, consume it with deduplication and retry, and register the two
long-running processes as CLI commands.

It assumes a PostgreSQL database and a RabbitMQ broker reachable
from your application. See [core/RELAY.md](core/RELAY.md) for the relay,
[amqp/TRANSPORT.md](amqp/TRANSPORT.md) for the AMQP publisher, and
[core/CLI_REFERENCE.md](core/CLI_REFERENCE.md) for every command's full option list.

The example uses the three packages: the core (`Freyr\MessageBroker\`), the
PostgreSQL adapter (`Freyr\MessageBroker\Adapter\PostgreSql\`) and the AMQP
adapter (`Freyr\MessageBroker\Adapter\Amqp\`). Today one Composer package
holds all three. The section [Send webhooks](#send-webhooks) uses the HTTP
adapter (`Freyr\MessageBroker\Adapter\Http\`) in place of the AMQP adapter.
The documents of each package are in `docs/core/`, `docs/postgresql/`,
`docs/amqp/` and `docs/http/`.

## Define a message

Userland messages extend `Message` and expose a named constructor that
builds the payload explicitly — there is no reflection-based normalization.
`id` and `createdAt` are generated by the base class; the payload is
whatever your named constructor puts in the array.

```php
use Freyr\MessageBroker\Message;

final class OrderPlaced extends Message
{
    public static function create(string $orderId, int $totalCents): self
    {
        return new self(name: 'order.placed', payload: [
            'order_id' => $orderId,
            'total_cents' => $totalCents,
        ]);
    }
}
```

## Produce inside your transaction

`OutboxProducer` writes through your application's own `PDO` connection, so
the outbox row commits or rolls back atomically with your own state change.
The producer opens no transaction itself: atomicity holds only inside the
transaction that your application opens.
`OutboxStore` is the storage interface; `PostgreSqlOutboxStore` is the shipped PDO
implementation — construct it with your connection.

The payload is encoded at produce time: `JsonWireFormat` turns it into the
exact bytes stored in the outbox `body` column, and a payload that cannot be
encoded throws inside your transaction — nothing commits.

```php
use Freyr\MessageBroker\Outbox\OutboxProducer;
use Freyr\MessageBroker\Adapter\PostgreSql\PostgreSqlOutboxStore;
use Freyr\MessageBroker\Serializer\JsonWireFormat;

$pdo = new PDO($dsn, $user, $password, [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]);
$outbox = new PostgreSqlOutboxStore($pdo);
$producer = new OutboxProducer($outbox, new JsonWireFormat(), lane: 'orders');

$pdo->beginTransaction();
// ... your own state change ...
$producer->produce(OrderPlaced::create('o-1', 4999), headers: ['correlation_id' => 'c-1']);
$pdo->commit(); // the outbox row commits atomically with your data
```

A *lane* is a named drain of the outbox table. One producer instance writes
to one lane. Any number of identical relay workers drain that lane, and rows
publish in any order, so consumers must be order-insensitive.

## Run the schema setup

Before producing anything, create `outbox_messages` (a table partitioned by
`created_at`, one partition per UTC day, no default partition),
`message_deduplication`, and `dead_letters`. The command also creates the
first daily partitions:

```bash
php bin/console message-broker:setup:schema
```

The `body` column is `BYTEA`. `--premake-days` (default `3`) sets how many
days of partitions
the command creates ahead. See [core/CLI_REFERENCE.md](core/CLI_REFERENCE.md) for
`--dump-sql` and every other command's options.

## Run a relay

A relay drains one outbox lane to one transport target. Each relay worker
claims a batch of rows with `FOR UPDATE SKIP LOCKED`, publishes the batch with
publisher confirms, and marks the rows published. It never deletes rows. It
needs a dedicated `AMQPChannel` — publisher confirms are channel-global
state, so nothing else may publish on the same channel.

```php
use Freyr\MessageBroker\Outbox\Relay;
use Freyr\MessageBroker\Adapter\Amqp\AmqpMessagePublisher;
use Freyr\MessageBroker\Adapter\Amqp\AmqpPublishConfig;

$relay = new Relay(
    outbox: $outbox,
    publisher: new AmqpMessagePublisher(
        $channel,                                    // a dedicated PhpAmqpLib AMQPChannel
        new AmqpPublishConfig(exchange: 'orders'),
        JsonWireFormat::CONTENT_TYPE,
    ),
    lane: 'orders',
);
$relay->run(); // blocks; SIGTERM/SIGINT to stop
```

Run more workers on the same lane to scale throughput; each worker has its
own database connection and its own channel. See
[core/RELAY.md](core/RELAY.md) and [amqp/TRANSPORT.md](amqp/TRANSPORT.md) for the details.

## Schedule the outbox maintenance

Rows stay in `outbox_messages` until their daily partition expires. There is
no default partition, so an insert for a day with no partition fails. Run
`message-broker:outbox:maintain` once a day to create the upcoming partitions
and drop the expired ones:

```php
use Freyr\MessageBroker\Console\OutboxMaintainCommand;
use Freyr\MessageBroker\Adapter\PostgreSql\PostgreSqlOutboxRetention;

$application->add(new OutboxMaintainCommand(new PostgreSqlOutboxRetention($pdo)));
```

```bash
php bin/console message-broker:outbox:maintain --retention-days=7 --premake-days=3
```

An expired partition that still holds unpublished rows is kept, and the
command exits with code 1; `--drop-unpublished` drops it with those rows. See
[core/CLI_REFERENCE.md](core/CLI_REFERENCE.md) for the options and the exit codes, and
[postgresql/RETENTION.md](postgresql/RETENTION.md) for the retention rules and pg_partman.

## Run a consumer

A consumer deserializes each delivery, deduplicates and dispatches inside
one database transaction, then acks. Failures go through a per-transport
retry policy and land in the shared `dead_letters` table once the attempt
budget is exhausted.

```php
use Freyr\MessageBroker\Consumer\CallableDispatcher;
use Freyr\MessageBroker\Consumer\IncomingMessage;
use Freyr\MessageBroker\Adapter\PostgreSql\PostgreSqlDeadLetterStore;
use Freyr\MessageBroker\Consumer\DeliveryProcessor;
use Freyr\MessageBroker\Retry\Backoff;
use Freyr\MessageBroker\Retry\ExponentialRetryPolicy;
use Freyr\MessageBroker\Serializer\JsonDeserializer;
use Freyr\MessageBroker\Adapter\PostgreSql\PdoTransaction;
use Freyr\MessageBroker\Adapter\Amqp\AmqpConsumer;
use Freyr\MessageBroker\Adapter\Amqp\AmqpQueueConfig;
use Freyr\MessageBroker\Adapter\PostgreSql\PostgreSqlDeduplicationStore;

$consumer = new AmqpConsumer(
    channel: $channel,
    queue: new AmqpQueueConfig('orders_q'),
    processor: new DeliveryProcessor(
        deserializer: new JsonDeserializer(),
        dispatcher: new CallableDispatcher(static function (IncomingMessage $m): void {
            // your handler — denormalize $m->payload and act
        }),
        transaction: new PdoTransaction($pdo), // the SAME connection as the dedup store and the handler
        deduplication: new PostgreSqlDeduplicationStore($pdo),
        retryPolicy: new ExponentialRetryPolicy(maxAttempts: 5, backoff: Backoff::exponential(initialDelayMs: 1_000, maxDelayMs: 300_000)),
        deadLetters: new PostgreSqlDeadLetterStore($pdo),
        name: 'orders_consumer',
        maxDeliveries: 5, // the delivery limit (the default); null turns it off
    ),
);
$consumer->run(); // blocks
```

`DeliveryProcessor` holds the transport-neutral exactly-once algorithm and
imports no AMQP class. `AmqpConsumer` is the AMQP loop around it.

`maxDeliveries` is the delivery limit: a message that stopped the process five
times (five deliveries that ended with no ack) becomes a dead letter with the
error `DeliveryLimitExceeded`, and the handler does not run again. Only a
quorum queue gives the delivery count. Keep the value not higher than
`x-delivery-limit` of the queue. See
[core/CONSUMER.md](core/CONSUMER.md#delivery-limit) and
[amqp/CONSUMER.md](amqp/CONSUMER.md#the-return-rule).

`name` scopes deduplication — the same message id delivered to two
differently-named consumers is processed by both; delivered twice to the
same named consumer is processed once.

## Register the CLI

Relays and consumers are long-running processes. Register each one as a
named callable on `RelayRunCommand`/`ConsumeCommand` so an operator (or a
supervisor) starts it by lane/consumer name:

```php
use Freyr\MessageBroker\Console\ConsumeCommand;
use Freyr\MessageBroker\Console\RelayRunCommand;
use Freyr\MessageBroker\Worker\WorkerLimits;

$application->add(new RelayRunCommand(['orders' => static fn (WorkerLimits $limits) => $relay->run($limits)]));
$application->add(new ConsumeCommand(['orders' => static fn (WorkerLimits $limits) => $consumer->run($limits)]));
```

Run them with `php bin/console message-broker:relay:run orders` and
`php bin/console message-broker:consume orders`. Each command gives the
callable a `WorkerLimits` from its options (`--limit`, `--time-limit`,
`--memory-limit`, and `--failure-limit` for `consume`), for example
`php bin/console message-broker:consume orders --time-limit=3600 --memory-limit=128M`. Deploy both under a process
supervisor with restart-always — see [core/PRODUCTION.md](core/PRODUCTION.md) for the
crash-only deployment model and why it is safe.

## Send webhooks

The webhook queue sends the same messages to the HTTP endpoints of
subscribers. It uses the core, the PostgreSQL adapter and the HTTP adapter
(`Freyr\MessageBroker\Adapter\Http\`, needs `symfony/http-client` and
`symfony/http-foundation`). It does not use the outbox, the relay or AMQP.

Your application owns the subscriptions and gives them through
`Webhook\SubscriptionProvider`. The ID of a subscription is the lane of its
deliveries:

```php
use Freyr\MessageBroker\Webhook\Subscription;
use Freyr\MessageBroker\Webhook\SubscriptionProvider;

final class CrmSubscriptions implements SubscriptionProvider
{
    public function forMessage(string $messageName): array
    {
        return $messageName === 'order.placed' ? [$this->crm()] : [];
    }

    public function find(string $lane): ?Subscription
    {
        return $lane === 'crm' ? $this->crm() : null;
    }

    public function lanes(): array
    {
        return ['crm'];
    }

    private function crm(): Subscription
    {
        return new Subscription('crm', 'https://crm.example.com/hooks/orders', ['whsec_MfKQ9r8GKYqrTwjUPD8ILPZIo2LaLaSw']);
    }
}
```

Create the table `webhook_deliveries` with
`php bin/console message-broker:webhook:setup`, then produce inside your
transaction. `WebhookProducer` writes one delivery row for each subscription
of the message:

```php
use Freyr\MessageBroker\Adapter\PostgreSql\PostgreSqlDeliveryStore;
use Freyr\MessageBroker\Serializer\JsonWireFormat;
use Freyr\MessageBroker\Webhook\WebhookProducer;

$subscriptions = new CrmSubscriptions();
$webhooks = new WebhookProducer($subscriptions, new PostgreSqlDeliveryStore($pdo), new JsonWireFormat());

$pdo->beginTransaction();
// ... your own state change ...
$webhooks->produce(OrderPlaced::create('o-1', 4999));
$pdo->commit();
```

Run the delivery loop with the HTTP sender, as a command. Each worker has its
own connection:

```php
use Freyr\MessageBroker\Adapter\Http\HttpDeliverySender;
use Freyr\MessageBroker\Adapter\Http\HttpSenderConfig;
use Freyr\MessageBroker\Adapter\PostgreSql\PostgreSqlDeliveryRetention;
use Freyr\MessageBroker\Adapter\PostgreSql\PostgreSqlDeliverySchemaInstaller;
use Freyr\MessageBroker\Console\WebhookMaintainCommand;
use Freyr\MessageBroker\Console\WebhookRunCommand;
use Freyr\MessageBroker\Console\WebhookSetupCommand;
use Freyr\MessageBroker\Webhook\DeliveryLoop;
use Freyr\MessageBroker\Webhook\DeliveryLoopConfig;

$sender = new HttpDeliverySender(new HttpSenderConfig(maxHostConnections: 100), logger: $logger);

$application->add(new WebhookSetupCommand(new PostgreSqlDeliverySchemaInstaller($pdo)));
$application->add(new WebhookMaintainCommand(new PostgreSqlDeliveryRetention($pdo)));
$application->add(new WebhookRunCommand(
    static fn (DeliveryLoopConfig $config) => new DeliveryLoop(
        new PostgreSqlDeliveryStore($workerPdo),
        $sender,
        $subscriptions,
        config: $config,
    ),
    new DeliveryLoopConfig(batchSize: 100),
));
```

Run `php bin/console message-broker:webhook:run` under a process supervisor,
and `message-broker:webhook:maintain` once a day. Each request is a signed
`POST` with the message ID in `webhook-id`. A delivery that fails each attempt
goes to `dead_letters` with the source `webhook:crm`, and `dlq:replay` sends it
again when `ReplayService` has the delivery store (the argument `deliveries:`,
see [core/DLQ_OPERATIONS.md](core/DLQ_OPERATIONS.md#replay-of-a-webhook-dead-letter)).
Keep `maxHostConnections` of the sender at the batch size of the loop
or more. The sender refuses an endpoint in a private network by default.
